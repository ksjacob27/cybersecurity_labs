✅ Task 1: Script Setup – Bash-Based Network Change Monitor

In this task, you will write a Bash script that monitors network changes across the 192.168.10.0/24 subnet. The script will be used to identify hosts and ports that appear, disappear, or change over time. You will implement it modularly, using functions, and design it to support comparison-based change detection.

🛠️ Instructions

Create a file called:

network_monitor.sh

Implement the following components in your script:

🔹 Step 1: Initialization & Setup

  • Create or define the following directories:
mkdir -p /home/kali/Documents/assignment3/scans
  • Define variables in your Bash script:
subnet="192.168.10.0/24"
output_dir="/home/kali/Documents/assignment3/scans"
log_file="/home/kali/Documents/assignment3/log.txt"
timestamp=$(date +"%Y-%m-%d_%H-%M")
scan_file="$output_dir/scan_$timestamp.txt"
current_state="$output_dir/current_state.txt"
previous_state="$output_dir/previous_state.txt"

🔹 Step 2: Host & Port Scanning

Use nmap to identify all active hosts and their open TCP ports:

nmap -sS -p- "$subnet" --open -oG "$scan_file"
  • -sS: SYN scan (stealthy, fast)
  • -p-: Scans all 65535 TCP ports
  • --open: Only show hosts with open ports
  • -oG: Grepable output for easier parsing

Ensure you handle errors if the scan fails or returns empty.

🔹 Step 3: Parse and Format Current Scan

After the scan_file is created, extract host IPs and open ports and copy them into current_state.txt:

awk '/Up$/{ip=$2} /Ports:/{split($0,a,"Ports: "); print ip " → " a[2]}' "$scan_file" | \
sed 's/\/open\/tcp//g' | sed 's/, /\n    Port: /g' > "$current_state"

The output will resemble:

192.168.10.6 → 21, 23, 80
192.168.10.7 → 22

This file will serve as the latest snapshot of the network state.

🔹 Step 4: Compare with Previous Scan (If Exists)

If previous_state.txt exists, compare it with current_state.txt and extract changes:

  • New hosts: Appear in current but not in previous
  • Missing hosts: Appear in previous but not in current
  • Port changes: For same host, compare port lists

You may use grep, comm, diff, or structured awk blocks.

After detection is complete, update the baseline:

cp "$current_state" "$previous_state"

On first run (when no previous state exists), treat it as the baseline.

🔹 Step 5: Log Output

Write structured messages to the log file with timestamps:

  • On first run:
echo "[$(date '+%Y-%m-%d %H:%M')] Initial scan:" >> "$log_file"
cat "$current_state" >> "$log_file"
  • On subsequent runs (if differences are found):
echo "[$(date '+%Y-%m-%d %H:%M')] Change detected:" >> "$log_file"
# Example additions to follow:
# + New host: 192.168.10.8
#     Open ports: 22, 8080
# + 192.168.10.4: Port 6200 opened
# - 192.168.10.6: Port 139 closed

Each entry should be easy to trace and audit. Avoid duplicating unchanged state.

🔒 Part 2: Network Defense Using IPTables on VM-D (70 pts)

🎯 Objective

You are the administrator of VM-D, a Linux web server running on port 80 (HTTP). Your task is to secure this host by implementing a stateful firewall using iptables. You must restrict all traffic except explicitly allowed service connections and harden the system against known attacks and misconfigurations.

🧱 Testbed

VM OS Role Services/Tools
VM-A Kali Linux Attacker hping3, curl, nmap, spoofed packet tools
VM-D Kali Linux Defender (Firewall) iptables, SSH server, Python web server
VM-T Target (M2) Metasploitable-2

🔧 Firewall Policy Requirements for VM-D

The main goal of this part is to implement the following access control policy on VM-D using iptables:

Default Policy

  • Set all default policies to DROP:
    • INPUT
    • OUTPUT
    • FORWARD
  • This ensures that all traffic is denied unless explicitly allowed by a rule.

Allow Legitimate Traffic

  • Allow the following outgoing connections from VM-D and their corresponding replies:

    • DNS queries: UDP packets to port 53, and their corresponding replies.
    • ICMP echo-requests and the corresponding incoming echo-replies.

  • Allow legitimate incoming connections and their corresponding replies:

    • HTTP (TCP port 80) connections from any internal source (belonging to 192.168.10.0/24 but not from any other source).
    • SSH (TCP port 22) connections only from VM-T (assumed to be the trusted admin IP).

Block Illegitimate Traffic

Drop the following:

  • All illegitimate TCP, UDP and ICMP packets (not explicitly authorized above).
  • Packets from spoofed or reserved IP ranges:
    • Packets coming from any range other than our internal network range.
    • Packets with srcIP = VM-D’s IP
    • Packets in the INVALID connection state (as determined by the conntrack module).
    • Any traffic not arriving via lo but claiming a source IP in 127.0.0.0/8.

Rate-Limiting Policies

  • Apply rate-limiting on HTTP (port 80):
    • Allow max 10 new connections/second, with a burst of 20.
    • Restrict concurrent HTTP sessions per IP (e.g., to 20 simultaneous connections).
  • Limit SSH login attempts:
    • e.g., allow max 3 new SSH connections/minute per IP.
  • Rate-limit SYN packets to mitigate SYN scans: allow 5 new SYN packets per second, with a burst of 10.

Logging Policy

  • Maintain clear and categorized logs to support traffic analysis and incident response.

  • Use specific logging prefixes to tag and differentiate types of suspicious or unauthorized activity:

    • SCAN-TCP: for detected TCP scan patterns (e.g., NULL, Xmas, SYN-FIN, ACK scans).
    • ILLEGAL-IP/PORT: for access attempts to restricted or unauthorized ports (e.g., SSH from untrusted IPs, external IPs (e.g. due to IP spoofing)).
    • DOS-RATE-LIMIT: for traffic exceeding defined rate limits (e.g., SYN floods, excessive HTTP or SSH attempts).
    • MALFORMED: for malformed or spoofed packets (e.g., invalid source IPs, source = destination IP).

  • Add a final generic logging rule:

    • Prefix: DROP-GENERIC
    • Purpose: capture and log all other unmatched and dropped packets for auditing or future policy refinement.
